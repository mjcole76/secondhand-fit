## Aloud (2026)
- Contest: YouCam API Skin AI & Apparel VTO Hackathon · Recorded result: 1st Place Winner (page labels it "Winner — 1st Place Winner") [Public Project Information]
- Problem: Beauty and skincare e-commerce is largely visual — product images, ingredient panels, and shade swatches are often unavailable to screen readers — so blind and low-vision shoppers cannot independently identify a product, learn its ingredients/allergens, or evaluate whether it suits their skin. The page frames this as both an access gap and a legal/compliance exposure for retailers, citing accessibility lawsuits against beauty retailers, 2025 ADA digital-accessibility filing counts, and the European Accessibility Act (claims sourced from the project page, not independently verified).
- Target user: Blind and low-vision beauty shoppers using a mobile browser (iOS screen-reader users specifically called out); secondarily beauty retailers/brands needing accessible, compliance-safe skin AI.
- Solution: A mobile web app (plus Capacitor iOS/Android shells) offering four fully non-visual flows operable with the screen off: a live WebRTC voice assistant that calls real ingredient/allergen tools; sound-guided barcode scanning with a layered spoken product read; a sound-framed selfie skin analysis grounded in YouCam Skin Analysis structured scores; and a post-makeup 'verify' capture compared against the session's bare-skin scores. Spoken output is constrained to cosmetic/appearance language, traceable to API scores, with explicit uncertainty disclosure.
- Technologies: Next.js, TypeScript, Vercel, Vercel AI SDK, WebRTC, OpenAI Realtime API, Deepgram, ElevenLabs, MediaPipe, html5-qrcode, Capacitor, YouCam Skin Analysis API, YouCam Skin Tone Analysis, YouCam MCP server, EU CosIng dataset, EU fragrance-allergen list (Regulation 2023/1545), Open Beauty Facts
- Sponsor integration depth: Core workflow
- Observed strengths: Observed strength: the sponsor API is wired end-to-end server-side (registration, upload, task creation, polling proxy) rather than superficially wrapped, with endpoint-level detail disclosed; Observed strength: explicit traceability rule — every spoken skin statement maps to a structured ui_score, and the face image is not sent to a general vision model for free-form description; Observed strength: accessibility is the core interaction model (screen-off operation, audio targeting, text mirroring) rather than an add-on setting; Observed strength: safety enforced in tooling (CI claim linter blocking medical language) instead of relying on prompt discipline alone; Observed strength: measured validation claim reported (10/10 non-visual captures accepted, each under 30 seconds on a real iPhone); Observed strength: grounding in named external datasets (EU CosIng inventory, EU fragrance-allergen regulation list, Open Beauty Facts) instead of free-form model knowledge; Observed strength: bias disclosure feature that lowers and verbalizes confidence based on skin-tone color metric and lighting quality; Observed strength: multiple working deliverables for judges — live web app, TestFlight build, Android APK, and open source repo; Observed strength: possible alignment with a sponsor-technology judging criterion, given the explicit 'Technological Implementation' section and use of the sponsor's MCP surface
- Observed weaknesses: Market, legal, and vendor statistics (lawsuit counts, conversion lift, API call volume, population figures) are asserted on the project page without linked sources in the captured text; Claims about the sponsor lacking an accessibility statement or VPAT are competitive assertions that would need independent verification; Heavy dependence on several third-party services (YouCam API, OpenAI Realtime, Deepgram, ElevenLabs, Open Beauty Facts) creates cost and availability risk; No pricing, deployment, or retailer-integration path described beyond the compliance argument; Broad scope (four flows, three distribution targets) makes depth per flow hard to assess from the page alone; No stated accuracy evaluation of the spoken ingredient/allergen answers themselves, only of capture acceptance rate
- URL: https://devpost.com/software/aloud-lxqr70

## ShadeSpan (2026)
- Contest: YouCam API Skin AI & Apparel VTO Hackathon · Recorded result: 2nd Place Winner (page shows "Winner — 2nd Place Winner"); submission date shown as Aug 17, 2026, so year is taken from the page and should be verified [Public Project Information]
- Problem: Apparel is typically photographed on a single model, so shoppers with different skin tones cannot judge how a garment's colour will read on them. Certain colours (beige, camel, chocolate) blend into particular skin tones, driving non-click or return. The page cites US clothing returns at 30–35% vs a 19.3% e-commerce average and ~23% of returns attributed to style and colour (figures as claimed on the page, unverified). Brands rarely detect this pre-launch because checking a 14-piece collection across six models would require 84 separate photo shoots.
- Target user: Merchandising teams and apparel brands auditing a catalogue before launch (brand-side, not shopper-side)
- Solution: A pre-launch catalogue audit pipeline: it takes a product catalogue plus a panel of six people spanning Fitzpatrick I–VI, renders every garment on every panelist via YouCam Apparel Virtual Try-On, scores each garment/skin-tone cell on colour separation using published colour science, grades each garment on its worst skin tone rather than the average, and outputs a report naming which garment fails on whom. A dashboard live mode accepts an ad-hoc product photo and returns six renders with scores in about 30 seconds.
- Technologies: Python, asyncio, httpx, pydantic, typer, FastAPI, uvicorn, Jinja2, numpy, Pillow, colour-science, CIEDE2000, WCAG contrast, YouCam API (Perfect Corp), Apparel VTO, Skin AI
- Sponsor integration depth: Core workflow
- Observed strengths: Observed strength: cross-validation framing — independent colour-science computation and generative renders are reported to agree across 84 cells, which the write-up itself flags as the key result; Observed strength: an explicit, defensible design decision (grade on the worst skin tone, not the mean) with a stated rationale about who the tool protects; Observed strength: fully explainable scoring using published standards (WCAG contrast, CIEDE2000) with no model opinions in the score; Observed strength: candid reporting of limitations — drift check accuracy stated as 10/14 by eye, and deliberately excluded from the grade; Observed strength: honest instrumentation (balance read from the account, per-render cost measured at 2 units rather than estimated); Observed strength: reframes the sponsor API from a shopper feature to a brand-side measuring instrument, with a cost argument supporting the inversion; Observed strength: substantial, specific API-integration documentation (endpoint versions, slugs, valid enum values, face-to-frame constraint) that is useful to other builders; Observed strength: reproducibility affordances — offline mock mode, content-addressed caching, single-file API adapter, centralized thresholds; Observed strength: narrative discipline — the challenge section describes a real failure (renders contradicting report claims) and the engineering response rather than hiding it; Observed strength: concrete, quantified demo outcome (14.3% of demo garments passing on all six tones) that is easy to show on screen
- Observed weaknesses: Panel consists of a single model per Fitzpatrick tone, so results per tone band rest on one face/body; the author lists multiple models per band as future work; Render-fidelity drift detection is acknowledged as imprecise (agrees with eye-check on 10 of 14 cells) and cannot be folded into scoring without real garment segmentation; Try-on engine sometimes returned the model's original clothing, especially with dark or structured source garments; partially mitigated by swapping panel photos rather than solved systematically; Skin tone is measured locally because the sponsor API has no colour-analysis feature, adding an unverified measurement step; Return-rate and returns-cause statistics are cited without sources on the page and need verification; Results are demonstrated on a small 14-item demo catalogue; no validation against a real brand's returns data yet; No commerce integration yet (Shopify/PIM hook listed as future work), so it is not embedded in a merchandising workflow; Sourcing openly licensed portraits across the full tone range was difficult, and the author notes deep-skin portraits often measure darker than the subject, a potential bias in the panel
- URL: https://devpost.com/software/shadespan

## CASTING (2026)
- Contest: YouCam API Skin AI & Apparel VTO Hackathon · Recorded result: Winner — 3rd–5th Place Winner (as shown on page) [Public Project Information]
- Problem: Brands photograph products on only one or two models, so no one in the company can answer which customers the catalogue never shows. There is no measured way for a merchandiser to know which skin tones a product's colorway serves or where it loses contrast before the product goes live.
- Target user: Brand-side catalogue owners — merchandisers running product pages, plus store managers asking whether a colorway serves their local customers (explicitly not consumers).
- Solution: Upload one product photo; the app fans out Perfect Corp / YouCam Apparel Virtual Try-On across a reference panel of eight AI-generated people with pre-measured skin profiles, then returns a 'coverage board' (same garment on eight measured skin tones, Fitzpatrick band labeled per tile) plus a coverage score identifying which Fitzpatrick bands are served and where the colorway loses contrast. Contrast diagnosis uses deterministic CIELAB color math (ΔL* primary, ΔE2000 secondary) over measured tone values, with no model or LLM. Outputs a PDP-ready image ZIP and a one-page coverage report.
- Technologies: Next.js (App Router), TypeScript, React, Node.js, Vercel, YouCam API, AI Clothes Virtual Try-On, AI Skin Analysis, AI Fitzpatrick Skin Type Analysis, AI Facial Color Tones Analyzer, CIELAB color math, NDJSON streaming
- Sponsor integration depth: Core workflow
- Observed strengths: Observed strength: clear inversion of the usual try-on use case — brand/merchandiser as user and a cohort rather than a single face; Observed strength: all four sponsor APIs are used in the core workflow, with the three Skin APIs supplying the measured basis for the scoring; Observed strength: deterministic, explainable scoring (ΔL*, ΔE2000 over measured values) rather than model-generated judgments; Observed strength: engineering robustness — parallel fan-out, NDJSON streaming, partial-failure reporting, server-side key handling, credit circuit-breaker with labeled fallback so cold visitors always see a working demo; Observed strength: prominent, specific self-disclosure of limits (curated AI-generated panel, sample size, unmeasurable Fitzpatrick II and V, fictional brand, precomputed runs labeled); Observed strength: concrete business-side deliverables (PDP image ZIP, one-page report) aimed at a real pre-launch workflow; Observed strength: loading experience derived from actual measured latencies rather than decorative animation; Observed strength: tight scope discipline — sizing and fit explicitly excluded
- Observed weaknesses: Reference panel is only eight AI-generated people, not real customers, limiting generalizability (acknowledged in the submission); Fitzpatrick II and V are not measurable with the current panel, so coverage is incomplete; No database, accounts, or permalinks, so runs are not persisted or shareable; Single colorway per run; direct colorway comparison is listed as future work; Runs are cost-capped (16 API units each), and cold visitors may see a precomputed run rather than a live one; Limited to apparel try-on; other VTO categories (shoes, bags, accessories) not yet supported; Contrast diagnosis is tone/contrast-only and does not address fit, sizing, or garment suitability
- URL: https://devpost.com/software/casting

## KeepMe (2026)
- Contest: YouCam API Skin AI & Apparel VTO Hackathon · Recorded result: Winner — 3rd–5th Place Winner (as shown on page) [Public Project Information]
- Problem: Generative AI virtual try-on can silently alter a shopper's identity — removing glasses, changing face, hair, skin appearance, body outline, or background — in ways that are subtle, personal, and hard to notice before the image is accepted. Consent in such tools is typically a vague checkbox rather than something software can enforce or verify.
- Target user: Shoppers using AI apparel virtual try-on (primary), plus retailers deploying try-on experiences who view privacy-filtered insights behind authenticated retailer views.
- Solution: A consent and visual-integrity layer wrapped around apparel virtual try-on. The shopper defines a machine-readable 'Identity Contract' specifying which regions AI may change (garment area) and which are protected (glasses, face, hair, skin, body shape, background, custom hand-drawn zones). Approved inputs are sent server-to-server to YouCam AI Clothes v3; the generated result is measured against the source with multiple integrity signals, classified (passed / needs review / failed / inconclusive / passed after repair), optionally repaired from the source and re-verified, and finally recorded in a signed integrity receipt that the shopper can approve — or the shopper can delete all session artifacts immediately.
- Technologies: Next.js 16, React 19, TypeScript, Node.js, FastAPI, Python, OpenCV, MediaPipe, PostgreSQL, Vercel, Vercel Blob, Vercel Services bindings, Clerk, JOSE/JWS, ClamAV, Sharp, OpenTelemetry, Vitest, Playwright, axe-core, YouCam AI Clothes v3 API, YouCam Skin Analysis API v2.1
- Sponsor integration depth: Core workflow
- Observed strengths: Observed strength: the sponsor API is on the critical path — generation runs live server-to-server through YouCam AI Clothes v3, with a second sponsor API used as an auxiliary signal; Observed strength: consent is expressed as a structured, machine-readable contract rather than a checkbox, giving the verification layer something concrete to enforce; Observed strength: explicit handling of uncertainty via an 'inconclusive' state and a rule that hard findings cannot be masked by an average score; Observed strength: verifiable output artifact (cryptographically signed receipt binding contract and result digests) rather than only a rendered image; Observed strength: full privacy lifecycle described — private upload, metadata stripping, malware scanning, private storage, server-only provider access, retention limits, verified deletion; Observed strength: transparent demo framing that labels the guided failure scenario as a controlled synthetic fixture separate from live results; Observed strength: production-grade engineering breadth — fail-closed boundaries, OpenTelemetry instrumentation, and unit, integration, browser, accessibility, and live smoke tests; Observed strength: repeatable judge-facing scenario that makes the core detect → restore → reverify value visible without depending on a random model failure
- Observed weaknesses: Key failure case is demonstrated with a synthetic fixture rather than an organically observed generator failure, so real-world drift-detection rates are not evidenced on the page; Detection thresholds are self-described as needing calibration on a larger consented evaluation set; Repair is limited — the team notes it needs to handle more occlusion boundaries; Broad architecture (Next.js app, FastAPI service, ClamAV, blob storage, signing, auth, telemetry) implies heavy operational surface for a small team; No accuracy, latency, or false-positive/false-negative figures are presented on the page; Retailer-side value is described but appears less developed than the shopper flow; Dependence on a single generation provider; provider webhooks are still listed as future work
- URL: https://devpost.com/software/keepme

## ConfidFit (2026)
- Contest: YouCam API Skin AI & Apparel VTO Hackathon (Apparel Virtual Try-On track) · Recorded result: Winner — 3rd–5th Place Winner (as displayed on the project page) [Public Project Information]
- Problem: Online fashion shoppers have to guess how a garment will look on them, which the page frames as a bad experience for shoppers and costly for brands. The team also frames a secondary problem: most try-on demos are thin one-call API wrappers rather than something a merchant can actually run as a paid product.
- Target user: Two stated user groups: Shopify fashion merchants/brands (who install, enable products, and pay) and their storefront shoppers (who upload a photo on a product detail page to preview a look).
- Solution: A Shopify app that embeds a generative apparel virtual try-on into the product detail page. Shoppers consent and upload a photo, the app sends an async try-on task to Perfect Corp's YouCam Apparel VTO API (cloth-v3) through a server-side path, polls via a completion worker, and renders the preview in a storefront modal with an 'Honest Label' stating it is a visual preview only and not a fit guarantee. Merchants get a go-live checklist, per-product enablement, trial and paid plans with metered billing on successful try-ons, usage warnings and hard caps, fair-use limits, and cohort purchase-confidence analytics that suppress results when sample sizes are too small.
- Technologies: TypeScript, Node.js, React, Shopify (Theme App Block, App Proxy, App Store, billing), Prisma, PostgreSQL, Fly.io (web + worker), YouCam Apparel VTO API (cloth-v3)
- Sponsor integration depth: Core workflow
- Observed strengths: Observed strength: the sponsor API is the core of the product experience rather than a side feature, wired through a full async task/polling architecture; Observed strength: shipped as a real, listed Shopify App Store app with a marketing site, not only a hackathon prototype; Observed strength: production concerns are explicitly covered — entitlement, metered billing, webhooks, abuse controls, retention scrub, worker health, and deploy hardening; Observed strength: deliberate honesty constraints, including a visible disclaimer, refusal to claim fit accuracy, and analytics that suppress lift claims at low sample sizes; Observed strength: clear safety/scope decisions such as blocking intimates and swim categories; Observed strength: security-conscious design keeping API keys server-side behind the Shopify App Proxy; Observed strength: write-up documents specific technical obstacles and fixes, giving the claims concrete grounding
- Observed weaknesses: No demo video, screenshots, or visual walkthrough described on the page, so the shopper experience must be taken on trust; Source code is a private snapshot rather than open, limiting public verification; No quantitative results on try-on quality, conversion, or merchant adoption are presented (consistent with the stated no-overclaiming policy, but it leaves impact unproven on the page); Scope is tied to a single platform (Shopify) and a single model version (cloth-v3); Engagement on the page is minimal (one like, no comments), offering little external signal
- URL: https://devpost.com/software/confidfit
