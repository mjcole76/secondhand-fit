# Feature Map (MVP Control)

Complete **P0 before P1**. Do not start P2 until P1 is solid. P3 is out of scope for the contest.

## P1 — Important for judging quality
| Feature | Supports | Acceptance | Status |
|---|---|---|---|
| **Empirical calibration harness and threshold provenance** — A scripted run of deliberately degraded inputs through the VTO endpoint, recording for each whether it errored, rendered plausibly, or returned the original clothing; results stored as CalibrationSample rows and converted into the centralised threshold file that the readiness checks use. | criterion: Technological Implementation — genuine effort and non-trivial, working implementation | Every threshold in the config file traces to at least one recorded calibration observation, and the run log is committed to the repository. | Not Started |
| **Silent-failure detection on returned renders** — Post-render comparison of the buyer's source photo and the render against the normalised garment to detect the known case where the endpoint returns the original clothing; surfaced as an explicit 'this render looks unreliable' warning with the reason, never hidden or silently retried. | criterion: Quality of the Idea — genuine understanding of the problem space; Potential Impact — solution addresses the stated problem | The pinned silent-failure fixture produces an 'unreliable' status and a visible warning rather than a clean success state. | Not Started |
| **Content-addressed render cache** — Renders cached by hash of the normalised garment bytes, buyer photo bytes and provider model/parameter version, with an explicit 'served from cache — no API units spent' note rather than a simulated delay. | criterion: Technological Implementation — working, non-trivial implementation with cost control | A repeated identical try-on returns source='cache' with no new ledger spend entry. | Not Started |
| **Public methods page documenting checks, thresholds and limitations** — In-product page explaining each readiness check, what it measures, its current threshold, how the threshold was derived from real API runs, what the product deliberately refuses to claim, and the known weaknesses (flatness is a proxy; background suppression is conservative). | criterion: Design — complete, coherent product experience; Potential Impact — credible, specific case | Every check listed in the code appears on /methods with a threshold, a provenance note and a stated limitation. | Not Started |
| **Seller insights: try-on counts and grade history with small-sample suppression** — Per-listing try-on counts and a timeline of readiness grades across retake attempts, with any percentage or rate replaced by 'not enough data yet' below a documented minimum sample size. | workflow: Workflow step 11: seller sees how many try-ons their listing generated | A listing below the sample threshold shows counts but no computed rate; grade history shows one point per readiness attempt. | Not Started |
| **Offline mock mode from pinned fixtures** — Environment-flagged mode that runs the entire seller and buyer flow from fixtures captured during real API runs, so reviewers can inspect the system without spending units or holding credentials. | requirement: Mandatory: Repository contains all instructions required for the project to be functional | With the mock flag set and no credentials configured, both flows complete and zero outbound provider requests occur. | Not Started |
| **Session data deletion and short retention on buyer assets** — Visible 'delete my data now' control plus an automatic expiry sweep for buyer selfies and renders, with confirmation that deletion completed. | criterion: Design — complete product experience; and consistency with the in-product consent promise | After deletion, the selfie, render, watchlist entries and consent record for the session are gone and the render URL no longer resolves. | Not Started |
| **Copy-guard CI lint and automated accessibility check** — CI job that fails the build if banned claim vocabulary (fit, true to size, measurements, authentic, condition grade, guarantee) appears in user-facing copy, plus axe-core checks on the main routes. | criterion: Quality of the Idea — anti-overclaiming enforced mechanically rather than by convention | Introducing a banned term into any user-facing string fails CI; axe reports no critical violations on the main routes. | Not Started |
